# Software Copyright / Patent Disclosure Skill

## 简介

本技能是一个 Claude Code 插件，用于在代码库中交互式发现可专利化的创意，并生成高质量的、律师可用的专利披露文档及草拟权利要求。同时支持软件著作权（软著）申请材料的辅助撰写与审查。

核心能力包括：

- **代码库探索**：自动分析代码库，发现潜在的新颖算法、架构和技术方案
- **专利候选发现**：对可专利化创意进行置信度评分，无需你事先判断哪些可申请专利
- **对话式访谈**：通过多轮对话提取隐性知识，使发明更具可辩护性
- **完整披露文档生成**：包含 12 个结构化章节、Mermaid 图表、伪代码和案例研究
- **权利要求草拟**：独立权利要求和从属权利要求，附带权利要求到代码的追溯映射
- **质量自评**：按专利委员会评分标准自我评估，并提出改进建议
- **软著申请辅助**：按中国版权保护中心规范辅助生成软件著作权登记材料

## 核心功能

### 1. 专利信息披露

交互式发现代码库中可专利化的创意，生成符合专利文书规范的完整披露文档：

- 自动从 git 历史检测发明人
- 对候选专利进行置信度评级
- 3 轮对话式问答捕获发明要点
- 生成 12 个结构化章节的披露文档
- 多智能体 QC 团队并行审查（首席律师、权利要求专家、技术审查员、冗余检测器、图表审计员、审查员）
- 输出 Google Doc 及本地中间产物

### 2. 软件著作权申请

按中国版权保护中心规范辅助撰写软著登记材料：

- 软件名称与版本号规范化
- 功能描述与技术特点撰写
- 源代码文档整理（前 30 页 + 后 30 页格式）
- 用户操作手册/设计说明书生成
- 申请表信息填报指导

### 3. 许可证分析与合规检查

对项目使用的开源许可证进行识别、分析和兼容性检查：

- 自动检测项目依赖的许可证类型
- 分析许可证之间的兼容性
- 识别专利条款风险（patent grant / retaliation）
- 生成合规报告

### 四种运行模式

| 模式 | 适用场景 | 功能说明 |
|------|----------|----------|
| **Full Discovery** | 不确定哪些可专利化 | 探索整个代码库，发现候选，生成完整披露 |
| **Targeted Analysis** | 已知要专利化的代码 | 指向特定文件/函数，跳过探索阶段 |
| **Quick Triage** | 需要快速评估 | 每个候选生成 1 页简报 — 追进/跳过/需更多信息 |
| **QC-Only** | 已有披露文档需优化 | 对现有本地披露或 Google Doc URL 重新运行 QC |

## 专利披露工作流程

Full Discovery 模式下，技能引导你完成 5 个阶段，每个阶段转换时有明确检查点：

| 阶段 | 内容 |
|------|------|
| **1. Explore** | 分析代码库，自动检测发明人，发现候选，你进行分诊 |
| **2. Deep-Dive** | 针对性代码分析 + 3 轮对话式问答，捕获发明要点 |
| **3. Generate** | 分批生成 12 个披露章节，每批有审查检查点 |
| **4. QC** | 六智能体 QC 团队并行审查；Writer 重写；循环至全部通过或达到 `qc_max_rounds`（默认 3） |
| **5. Output** | 发布 Google Doc；保存中间产物（disclosure.md, ids.json, qc-trail.md, qc-rounds/） |

### 增量会话

每个阶段完成后工作自动保存。你可以在中途停止，在新会话中恢复——插件读取 IDS JSON 并从上次中断处继续。

### 无本地代码？

如果不在 git 仓库中，技能会要求提供 GitHub URL，克隆仓库后进行分析。

## 披露文档结构

每个发明以 Google Doc 形式交付，本地保留中间产物：

```
patent-disclosures/<invention-slug>/
├── disclosure.md          # Mermaid 源码 Markdown
├── disclosure-export.md   # 含渲染 PNG 引用的版本
├── diagrams/              # 渲染的图表 PNG
├── ids.json               # 中间数据结构（结构化 JSON）
├── qc-trail.md            # 多智能体 QC 摘要
└── qc-rounds/             # 每轮原始发现 + Writer 输出（可审计追踪）
```

### 12 个披露章节

| # | 章节 | 用途 |
|---|------|------|
| 1 | Executive Summary | 非技术性概述，面向管理层 |
| 2 | Novelty | 真正新颖之处 — 发明步骤 |
| 3 | Context / Environment | 领域、系统环境、约束条件 |
| 4 | Problems Solved | 痛点和现有方案的失败 |
| 5 | Introduction | 背景概念和术语 |
| 6 | What It Does & How | 端到端技术描述，含图表 |
| 7 | Case Studies | 展示发明的真实场景 |
| 8 | Pseudocode | 语言无关的算法描述 |
| 9 | Data Structures | 模式、ER 图和数据流 |
| 10 | Implementation Details | 架构决策、ML 细节、权衡 |
| 11 | Alternatives | 与已知方案的比较 |
| 12 | Prior Art | 已知相关专利、论文、产品 |
| -- | **Draft Claims** | 独立权利要求 + 从属权利要求，含权利要求到代码映射 |

### 图表规范

图表在有价值时才包含（不强制每节都有）：

- **What It Does & How**：系统架构、处理流水线流程图（新颖步骤高亮）、序列图
- **Data Structures**：实体关系图
- **Implementation Details**：组件交互图
- **Case Studies**：演练图（推荐）

所有图表使用专利风格参考编号（如 "Processor 102"、"Step 302"）。

### 草拟权利要求

插件生成：

- **3+ 独立权利要求**（方法、系统、计算机可读介质）
- **8-12 从属权利要求**，用具体实现细节缩小范围
- **权利要求到代码映射** — 从每个权利要求元素追溯到源文件和行号

### 专利委员会评分标准

自我评估 4 个维度（1 = 最强，数值越高越弱）：

| 维度 | 评分 | 含义 |
|------|------|------|
| Technical Merit | 1-4 | 1=显著改进 ... 4=微小区别 |
| Alternatives | 1-4 | 1=无已知替代 ... 4=多种可行方案 |
| Value to Company | 1-4 | 1=关键战略 ... 4=仅防御性 |
| Infringement Detection | 1-3 | 1=易于检测 ... 3=需源代码 |

## 许可证分析

### 常见开源许可证对比

| 许可证 | 类型 | 专利条款 | 商业使用 | 需公开源码 | 兼容性 |
|--------|------|----------|----------|------------|--------|
| **MIT** | 宽松 | 无明确条款 | 允许 | 否 | 与几乎所有许可证兼容 |
| **Apache 2.0** | 宽松 | 明确专利授权 + 弱报复条款 | 允许 | 否 | 与 GPLv3 兼容，与 GPLv2 不兼容 |
| **BSD 2-Clause** | 宽松 | 无明确条款 | 允许 | 否 | 与几乎所有许可证兼容 |
| **BSD 3-Clause** | 宽松 | 无明确条款 | 允许 | 否 | 与几乎所有许可证兼容 |
| **GPLv2** | 强 Copyleft | 隐含授权 | 有条件 | 是 | 与 Apache 2.0 不兼容 |
| **GPLv3** | 强 Copyleft | 明确专利授权 + 弱报复条款 | 有条件 | 是 | 与 Apache 2.0 兼容 |
| **LGPLv3** | 弱 Copyleft | 明确专利授权 | 有条件 | 部分 | 与 Apache 2.0 兼容 |
| **AGPLv3** | 强 Copyleft（网络） | 明确专利授权 | 有条件 | 是 | 网络使用视为分发 |
| **MPL 2.0** | 弱 Copyleft（文件级） | 明确专利授权 + 弱报复 | 允许 | 部分 | 与 GPL 和 Apache 兼容 |

### 许可证兼容性矩阵

关键兼容性规则：

- **MIT / BSD** 可与几乎所有许可证组合，包括 GPL
- **Apache 2.0** 与 GPLv3 兼容，但与 GPLv2 不兼容（因专利条款冲突）
- **GPLv2 与 GPLv3** 之间不兼容，除非项目使用 "v2 or later" 选项
- **GPL 系列代码**一旦组合，整体必须以 GPL 分发
- **AGPL** 将网络使用视为分发，要求提供源码

```
兼容性简图（→ 表示可组合）：

MIT ──────→ GPLv2, GPLv3, Apache 2.0, BSD, MPL
BSD ──────→ GPLv2, GPLv3, Apache 2.0, MIT, MPL
Apache 2.0 → GPLv3, MIT, BSD, MPL
GPLv3 ────→ 仅 GPL 系列（整体须 GPLv3+）
GPLv2 ────→ 仅 GPL 系列（整体须 GPLv2）
AGPLv3 ───→ 仅 AGPL 系列
```

### 专利条款详解

开源许可证中的专利条款是合规检查的重点：

| 条款类型 | 说明 | 代表许可证 |
|----------|------|------------|
| **明确专利授权** | 贡献者授予免版税的专利使用权 | Apache 2.0, GPLv3, MPL 2.0 |
| **隐含专利授权** | 通过"不受限制地使用"等措辞隐含授权 | MIT, GPLv2 |
| **弱报复条款** | 若对本软件提起专利侵权诉讼，则终止你的许可 | Apache 2.0, GPLv3 |
| **强报复条款** | 若对许可方提起任何专利诉讼，则终止你的许可 | 较少见 |
| **无专利条款** | 不涉及专利权利 | BSD, MIT |

**风险提示**：MIT 和 BSD 许可证无明确专利条款，使用这些许可证的代码可能存在专利风险——贡献者未明确授予专利权，理论上可能就其专利主张权利。

## 专利风险评估

### 评估维度

对项目进行专利风险评估时，应关注以下维度：

1. **自有专利保护**
   - 代码中是否包含可专利化的新颖技术方案？
   - 是否已提交专利申请或披露文档？
   - 核心算法是否有防御性公开？

2. **第三方专利侵权风险**
   - 项目是否使用了可能受专利保护的技术？
   - 依赖库的许可证是否包含专利授权？
   - 是否在专利密集领域（如编解码、加密、AI 算法）？

3. **开源许可证专利条款**
   - 使用的依赖是否在 Apache 2.0 / GPLv3 下（有专利授权）？
   - 是否有依赖在 MIT / BSD 下（无明确专利授权）？
   - 是否存在许可证报复条款触发风险？

4. **商业发布风险**
   - 公开披露后是否丧失新颖性？（美国有 1 年宽限期，多数国家无宽限期）
   - 是否需要先提交临时专利申请再开源发布？

### 风险等级判定

| 等级 | 条件 | 建议措施 |
|------|------|----------|
| **高** | 专利密集领域 + 无专利授权依赖 + 商业产品 | 进行专利检索，考虑申请自有专利 |
| **中** | 部分专利风险依赖 + 有明确专利授权 | 审查依赖专利条款，保留授权记录 |
| **低** | 宽松许可证依赖为主 + 非专利密集领域 | 定期审查，保持许可证清单更新 |

## 软件著作权申请

### 申请流程

中国软件著作权登记通过中国版权保护中心（CPCC）办理，全流程如下：

```
注册账号 → 实名认证 → 填写申请表 → 准备材料 → 提交申请 → 审查受理 → 颁发证书
```

### 核心材料准备

#### 1. 源程序代码（PDF 格式）

- 提交前 30 页 + 后 30 页（不足 60 页提交全部）
- 每页不少于 50 行代码
- 删除空行、注释、行号
- 保证语法结构完整（括号闭合、标签匹配）
- 禁止提交加密或混淆代码
- 页眉包含软件名称和版本号，页码在右侧

#### 2. 软件文档（用户手册/操作说明，PDF 格式）

- 需包含功能模块、操作步骤（配截图）、技术特点
- 前后各 30 页（不足 60 页提交全部）
- 每页不少于 30 行文字
- 截图中的软件名称须与申请名称一致

#### 3. 其他材料

- **合作开发协议**：多人开发需提供，明确著作权分配
- **委托开发证明**：企业委托第三方开发时需提交
- **申请确认签章页**：A4 竖版打印，个人手写签字/企业盖鲜章后扫描上传

### 软件命名规范

| 要素 | 合规要求 | 风险示例 |
|------|----------|----------|
| 后缀 | 必须包含"软件""系统""平台""APP"等 | 错误："智能考勤" → 正确："智能考勤管理系统" |
| 禁用词 | 不得含地名、行业资质词 | 错误："杭州税务申报系统" |
| 商标冲突 | 禁用未授权第三方商标 | 错误："华为云监控软件"（无授权） |
| 版本号 | 推荐"V1.0"格式 | 正确：V1.0, V2.1 |

### 审查周期

| 阶段 | 平均耗时 | 状态流转 |
|------|----------|----------|
| 提交 → 受理 | 5-7 天 | 待受理 → 待审查 |
| 审查 → 发放 | 45-55 天 | 待审查 → 待发放 → 已发放 |
| 总周期 | 50-60 天 | 一次性通过 |

### 常见补正问题及应对

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| 代码页数不足 | 不足 60 页且未提交全部 | 补充代码或提交全部代码 |
| 文档缺少操作截图 | 用户手册无界面截图 | 添加功能截图，确保名称一致 |
| 著作权人信息不一致 | 多处材料中名称不统一 | 核对所有文件，确保名称完全一致 |
| 签章页使用电子签名 | CPCC 要求手写签字/鲜章 | 打印后手签/盖鲜章扫描上传 |
| 软件名称含 AI/GPT 等词 | 涉及生成式 AI 需额外声明 | 提交合规及原创性声明文件 |
| 截图出现其他单位标识 | 被要求证明合作关系 | 修改文档或提交合作开发协议 |

### 软著申请的实际用途

- **平台上线**：应用商店、小程序上线需提交软著证书
- **融资估值**：作为知识产权资产提升项目估值
- **项目招投标**：参与政府或企业项目的重要资质
- **法律维权**：遇到抄袭时作为法律证据
- **高企认定**：软著可作为 II 类知识产权加分
- **税收优惠**：国内企业可享受软件相关税收减免

## 合规检查流程

### 项目合规检查清单

```
1. 许可证清单
   ├── 列出所有直接依赖的许可证
   ├── 列出所有间接依赖的许可证
   └── 标记许可证类型（宽松 / Copyleft / 专有）

2. 兼容性验证
   ├── 检查许可证之间是否兼容
   ├── 检查 Copyleft 传播范围
   └── 检查专利条款覆盖情况

3. 义务履行
   ├── 许可证声明保留（MIT, BSD, Apache）
   ├── 源代码提供义务（GPL 系列）
   ├── 修改声明（Apache 2.0 NOTICE）
   └── 专利授权/报复条款记录

4. 风险评估
   ├── 专利侵权风险
   ├── 商标使用风险
   └── 出口合规风险

5. 文档归档
   ├── LICENSE 文件
   ├── THIRD-PARTY-NOTICES 文件
   ├── 依赖清单（package.json / go.mod 等）
   └── 合规报告
```

### 使用本技能进行合规检查

```
> 分析这个项目的许可证合规情况
> 检查我的依赖是否有专利风险
> 生成 THIRD-PARTY-NOTICES 文件
```

## 实际示例

### 示例 1：发现代码库中的可专利化创意

```
> /patent-disclosure

技能：正在分析代码库...
技能：发现 3 个潜在可专利化候选：
  1. [置信度: 高] 自适应缓存淘汰算法 (src/cache/adaptive-evictor.ts)
  2. [置信度: 中] 分布式任务调度去重机制 (src/scheduler/dedup.ts)
  3. [置信度: 低] 日志压缩编码方案 (src/logging/compress.ts)

你：深入分析第 1 个候选

技能：进入 Deep-Dive 阶段...
技能：第 1 轮问答 — 请描述这个算法与 LRU/LFU 的关键区别？
你：它根据访问频率的时间衰减动态调整权重...
```

## 最佳实践

### 专利披露

1. **尽早披露**：在公开发布代码前完成专利披露，避免丧失新颖性
2. **增量会话**：利用增量保存功能，不必一次完成所有阶段
3. **对话质量**：Deep-Dive 阶段的问答越详细，披露文档质量越高
4. **QC 迭代**：不要跳过 QC 阶段，多轮审查能显著提升文档质量
5. **权利要求映射**：确保每个权利要求元素都能追溯到具体代码行

### 软著申请

1. **开发完成即申请**：养成开发完成即申请的习惯，尤其 APP 上线、项目交付前
2. **命名规范**：软件名称必须包含"软件""系统""平台"等后缀，避免营销化表达
3. **代码整理**：用纯文本编辑器去除 IDE 格式，保存为 UTF-8 编码的 PDF
4. **材料一致性**：确保软件名称在所有文件中完全一致
5. **多人开发**：所有著作权人需提前完成实名认证
6. **AI 相关**：软件名称涉及 AI/GPT 等词需额外提交合规声明

### 许可证合规

1. **建立清单**：维护项目所有依赖的许可证清单
2. **定期审查**：每次添加新依赖时检查许可证兼容性
3. **优先宽松**：优先选择 MIT/Apache 2.0 许可的依赖，减少合规负担
4. **专利意识**：在专利密集领域优先选择有明确专利授权的许可证（Apache 2.0, GPLv3）
5. **Copyleft 警惕**：使用 GPL 系列依赖时，明确其传播范围和源码公开义务
6. **文档保留**：保留所有第三方许可证声明和 NOTICE 文件
