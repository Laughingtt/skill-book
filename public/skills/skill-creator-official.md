# Skill Creator (Official)

Anthropic官方Skill Creator技能，是创建、修改和优化Agent Skills的专业工具。它不仅是一个技能生成器，更是一个完整的技能开发工作流系统，支持测试驱动开发、性能基准测试和触发精度优化。

## 简介

### 什么是 Skill Creator

Skill Creator 是 Anthropic 官方提供的"元技能"——一个用于创建其他技能的技能。它将技能开发从"写完就祈祷"的模式转变为"测试-测量-改进"的工程化流程。

### 为什么 Anthropic 创建它

在 Skills 系统推出初期，开发者创建技能后往往面临两个核心问题：

1. **触发不可靠**：技能描述写得很好，但 Agent 在应该调用时没有调用，或者在不该调用时错误触发
2. **质量无法验证**：技能写完后缺乏系统化的测试方法，只能靠实际使用中发现问题

Anthropic 团队在自己优化六个内置文档技能时发现，即使是由系统设计者编写的技能，也存在触发精度问题。这促使他们开发了 Skill Creator，将评估和优化能力内置到技能创建流程中。

### Agent Skills 格式规范

Agent Skills 是一个开放标准格式，最初由 Anthropic 开发，现已被 OpenAI Codex、Cursor、Gemini CLI 等多个平台采纳。核心规范：

- **开放性**：SKILL.md 格式完全公开，任何 AI 平台都可以实现
- **标准化结构**：统一的目录结构和元数据格式
- **渐进式披露**：三级加载机制，高效管理上下文

## Skill 文件结构

### 基础结构

```
my-skill/
├── SKILL.md           # 必需：主技能文件
├── scripts/           # 可选：可执行代码
│   ├── validate.py    # 验证脚本
│   └── process.sh     # 处理脚本
├── references/        # 可选：参考文档
│   ├── api-guide.md   # API 指南
│   └── examples/      # 示例目录
└── assets/            # 可选：资源文件
    └── template.docx  # 模板文件
```

### YAML Frontmatter 字段

```yaml
---
name: skill-name                    # 必需：技能标识符
description: 技能描述和触发条件        # 必需：决定何时触发
compatibility: python>=3.8          # 可选：依赖要求
effort: high                        # 可选：努力级别
context: fork                       # 可选：子代理上下文
agent: Explore                      # 可选：子代理类型
paths: "src/**/*.py"                # 可选：路径限制
---
```

**字段规范**：

| 字段 | 必需 | 说明 |
|------|------|------|
| `name` | 是 | 小写字母、数字、连字符，最长64字符，不能以连字符开头/结尾 |
| `description` | 是 | 最长1024字符，必须说明技能功能和触发时机 |
| `compatibility` | 否 | 工具或运行时依赖 |
| `effort` | 否 | low/medium/high/xhigh/max |
| `context` | 否 | 设为 `fork` 在隔离子代理中运行 |
| `agent` | 否 | 子代理类型（Explore/Plan/general-purpose） |
| `paths` | 否 | Glob 模式，限制技能激活的文件范围 |

### 完整示例

```yaml
---
name: csv-analyzer
description: 分析和处理CSV数据文件，生成图表和统计报告。当用户提到CSV、数据分析、数据清洗、生成图表或需要处理表格数据时使用此技能。
---

# CSV Analyzer

分析CSV文件并生成可视化报告的专业工具。

## 工作流程

1. **数据探索**
   - 读取CSV文件，识别列类型
   - 统计行数、列数、缺失值
   - 展示数据样本

2. **数据清洗**
   - 处理缺失值（删除/填充）
   - 标准化格式
   - 去除重复行

3. **分析与可视化**
   - 计算统计指标
   - 生成图表（柱状图、折线图、散点图）
   - 输出分析报告

## 输出格式

- 清洗后的CSV文件
- PNG格式图表
- Markdown格式分析报告

## 注意事项

- 大文件（>100MB）需要分块处理
- 中文编码优先使用UTF-8
- 图表需要标注数据来源
```

### 渐进式披露机制

Skills 使用三级加载系统，高效管理上下文窗口：

| 级别 | 内容 | 加载时机 | 大小建议 |
|------|------|----------|----------|
| 第一级 | name + description | 始终在上下文中 | ~100词 |
| 第二级 | SKILL.md 正文 | 技能触发时加载 | <500行 |
| 第三级 | 捆绑资源 | 按需读取 | 无限制 |

**关键原则**：
- SKILL.md 保持精简，核心指令控制在500行以内
- 详细文档放入 `references/` 目录
- 可执行脚本放入 `scripts/` 目录，无需加载即可执行

## 创建流程

### 第一步：捕获意图

理解用户想要创建什么样的技能。如果当前对话中已有相关工作流，从中提取信息：

1. **技能目标**：这个技能让 Claude 能做什么？
2. **触发条件**：什么用户短语/场景应该触发？
3. **输出格式**：期望的输出是什么？
4. **测试需求**：是否需要设置测试用例？

**示例对话**：
```
用户：我想创建一个技能，帮我分析服务器日志，找出错误模式

Skill Creator：
- 这个技能应该处理哪些日志格式？（nginx、应用日志、系统日志）
- 触发短语可能是什么？（"分析日志"、"检查错误"、"日志里有什么问题"）
- 输出格式？（错误摘要、时间线、建议修复）
- 需要测试用例吗？（建议创建，日志分析有明确的正确/错误结果）
```

### 第二步：访谈与研究

主动询问边缘情况、输入输出格式、示例文件、成功标准和依赖项。

检查可用的 MCP 工具，研究相关文档和最佳实践。

### 第三步：编写 SKILL.md

基于用户访谈填写各组件：

```yaml
---
name: log-analyzer
description: 分析服务器日志文件，识别错误模式、异常请求和性能问题。当用户提到"分析日志"、"检查错误"、"日志问题"、"服务器日志"或需要排查系统问题时使用。
---

# Log Analyzer

## 工作流程

1. 使用 Glob 定位日志文件：`*.log`, `logs/*.log`, `/var/log/*.log`
2. 使用 Grep 搜索错误模式：ERROR, FATAL, Exception, Traceback
3. 按类型和频率分组错误
4. 按频率排序输出摘要

## 输出格式

### 错误摘要
- 错误类型
- 出现次数
- 首次/末次出现时间
- 示例堆栈

### 建议
- 可能原因
- 修复建议
```

### 第四步：创建测试用例

编写2-3个真实测试提示，保存到 `evals/evals.json`：

```json
{
  "skill_name": "log-analyzer",
  "evals": [
    {
      "id": 1,
      "prompt": "我的nginx日志在 /var/log/nginx/error.log，帮我看看最近有什么错误",
      "expected_output": "错误摘要，包含错误类型、频率和时间范围"
    },
    {
      "id": 2,
      "prompt": "这个应用日志里有很多Java异常，能帮我分类吗？文件在 logs/app.log",
      "expected_output": "按异常类型分类的统计报告"
    }
  ]
}
```

### 第五步：运行测试

为每个测试用例生成两个运行：
- **with_skill**：使用技能的运行
- **without_skill**：不使用技能的基线运行

使用子代理并行执行，捕获时间和令牌数据。

### 第六步：评估与迭代

生成评估查看器，让用户审查结果：

```bash
python eval-viewer/generate_review.py \
  --skill-name "log-analyzer" \
  --workspace "log-analyzer-workspace/iteration-1"
```

根据用户反馈改进技能，重复测试直到满意。

## 修改与优化

### 四种工作模式

Skill Creator 2.0 提供四种模式：

| 模式 | 用途 | 工作流 |
|------|------|--------|
| **Create** | 创建新技能 | 访谈 → 研究 → 起草 → 测试 → 完善 |
| **Eval** | 测试技能性能 | 执行器 → 评分器 → 结果 |
| **Improve** | 迭代优化技能 | 执行器 → 评分器 → 比较器 → 分析器 → 应用 |
| **Benchmark** | 标准化性能测量 | 3次运行 → 聚合 → 分析 |

### 改进循环

1. **分析失败原因**
   - 阅读执行日志，找出问题根源
   - 区分指令歧义、缺失步骤、边缘情况

2. **泛化反馈**
   - 不要针对特定测试用例打补丁
   - 找出底层模式，改进通用指令

3. **保持精简**
   - 移除无效指令
   - 合并重复步骤
   - 将复杂逻辑移入脚本

4. **解释原因**
   - 使用推理式指令而非僵化规则
   - "做X因为Y会导致Z" 比 "必须做X" 更有效

### 盲比较（高级功能）

对于需要严格比较两个技能版本的情况：

1. **比较器**：将两个输出给独立代理，不告知来源
2. **分析器**：分析获胜者获胜的原因
3. **生成改进建议**

## 性能评估

### 评估指标体系

| 指标 | 说明 | 重要性 |
|------|------|--------|
| **通过率** | 断言通过百分比 | 核心质量指标 |
| **时间成本** | 执行耗时（秒） | 效率指标 |
| **令牌消耗** | 总令牌数 | 成本指标 |
| **方差** | 多次运行的标准差 | 稳定性指标 |

### 断言设计原则

**好的断言**：
- "输出包含有效的JSON文件" — 可程序验证
- "图表有标注的坐标轴" — 具体可观察
- "报告包含至少3条建议" — 可计数

**弱的断言**：
- "输出很好" — 太模糊
- "输出使用精确短语'总收入：$X'" — 太脆弱

### 评估工作流

```
测试用例 → 执行器 → 输出 → 评分器 → grading.json
                              ↓
                         聚合 → benchmark.json
                              ↓
                         分析器 → 改进建议
```

### 结果解读

**benchmark.json 示例**：

```json
{
  "run_summary": {
    "with_skill": {
      "pass_rate": {"mean": 0.83, "stddev": 0.06},
      "time_seconds": {"mean": 45.0, "stddev": 12.0},
      "tokens": {"mean": 3800, "stddev": 400}
    },
    "without_skill": {
      "pass_rate": {"mean": 0.33, "stddev": 0.10},
      "time_seconds": {"mean": 32.0, "stddev": 8.0},
      "tokens": {"mean": 2100, "stddev": 300}
    },
    "delta": {
      "pass_rate": 0.50,
      "time_seconds": 13.0,
      "tokens": 1700
    }
  }
}
```

**delta 解读**：
- 通过率提升50个百分点 — 显著价值
- 时间增加13秒 — 可接受
- 令牌增加1700 — 需权衡

### 模式分析

评估后检查：

1. **无区分度断言**：两种配置都通过的断言，考虑移除
2. **始终失败断言**：检查断言是否合理或测试太难
3. **高方差评估**：可能不稳定，需要收紧指令
4. **时间异常**：检查执行日志找出瓶颈

## 触发精度优化

### 为什么触发优化很重要

description 字段是技能触发的核心机制。Anthropic 在优化自己的六个内置文档技能时，发现5个技能的触发精度有提升空间。

常见问题：
- **欠触发**：应该触发时没有触发
- **过触发**：不该触发时错误触发

### 触发评估查询生成

创建20个评估查询，混合应该触发和不应触发的场景：

```json
[
  {"query": "帮我分析这个CSV文件的销售数据", "should_trigger": true},
  {"query": "这个表格需要清洗一下，有很多空值", "should_trigger": true},
  {"query": "能不能把数据画成图表", "should_trigger": true},
  {"query": "帮我写一个Python函数", "should_trigger": false},
  {"query": "这个PDF文件打不开", "should_trigger": false},
  {"query": "数据库连接失败了", "should_trigger": false}
]
```

**好的查询特征**：
- 真实用户会输入的内容
- 包含具体细节（文件路径、列名、上下文）
- 有不同长度和正式程度
- 边缘情况而非明显案例

### 优化循环

1. **生成查询集**：20个混合触发/不触发查询
2. **用户审查**：通过HTML模板让用户调整
3. **运行优化**：自动迭代优化description（60%训练集/40%测试集，每条查询运行3次，最多5轮迭代）
4. **选择最佳**：基于测试集得分选择（避免过拟合）

### 触发机制理解

技能出现在 Claude 的 `available_skills` 列表中，包含 name + description。Claude 根据描述决定是否咨询技能。

**关键洞察**：Claude 只在任务超出其基础能力时才咨询技能。简单的单步查询（如"读取这个PDF"）可能不会触发技能，即使描述完美匹配。

**建议**：评估查询应该足够复杂，让 Claude 确实需要技能帮助。

## 最佳实践

### 技能设计原则

1. **渐进式披露**
   - SKILL.md < 500行
   - 详细文档放 references/
   - 可执行脚本放 scripts/

2. **推理优于规则**
   - 解释为什么重要
   - 避免僵化的"必须"/"永远不"
   - 让模型理解意图

3. **精简有效**
   - 移除无效指令
   - 合并重复步骤
   - 每条指令都要有价值

4. **防御性设计**
   - 处理边缘情况
   - 提供错误恢复路径
   - 明确失败模式

### Description 编写技巧

```yaml
# 差的描述
description: 如何构建仪表板

# 好的描述
description: 构建数据仪表板显示内部指标。当用户提到仪表板、数据可视化、内部指标或需要展示公司数据时使用，即使没有明确说"仪表板"。
```

**技巧**：
- 包含功能描述和触发场景
- 使用"当...时使用"句式
- 覆盖同义词和相关概念
- 稍微"激进"一点以对抗欠触发倾向

### 测试用例设计

1. **从2-3个开始**，不要过早投入
2. **变化提示风格**：正式/随意、详细/简洁
3. **覆盖边缘情况**：异常输入、模糊请求
4. **使用真实上下文**：文件路径、列名、用户背景

### 常见陷阱

| 陷阱 | 表现 | 解决方案 |
|------|------|----------|
| 过度拟合 | 只对测试用例有效 | 泛化改进，测试更多场景 |
| 指令膨胀 | 添加越来越多规则 | 移除无效指令，保持精简 |
| 僵化规则 | 使用大量"必须"/"永远" | 改用推理式指令 |
| 忽略日志 | 只看输出不看过程 | 阅读执行日志找根因 |

## 常见问题

### Q: Skill Creator 和手动写技能有什么区别？

A: Skill Creator 提供完整的测试-评估-优化工作流。手动写技能后，你只能靠实际使用发现问题；Skill Creator 让你在发布前就验证技能质量。

### Q: 需要编程知识吗？

A: 基础技能创建不需要编程。但如果需要脚本验证或复杂处理，Python/Bash 知识会有帮助。

### Q: 评估需要多长时间？

A: 首次创建技能约15-30分钟。完整评估循环（3次迭代）约1-2小时。

### Q: 为什么我的技能没有被触发？

A: 常见原因：
1. description 不够具体
2. 任务太简单，Claude 不需要技能
3. 与其他技能冲突
4. 路径限制不匹配

使用 Skill Creator 的描述优化功能可以系统解决触发问题。

### Q: 如何处理技能之间的冲突？

A: 在 description 中明确边界。例如："用于X场景，不适用于Y场景（请使用other-skill）"。

### Q: 技能可以调用其他技能吗？

A: 可以。在指令中说明何时应该调用其他技能，Claude 会自动处理。

### Q: 如何分享技能给团队？

A: 三种方式：
1. Git 仓库：团队克隆到本地技能目录
2. skills.sh：发布到公共或私有仓库
3. 组织部署：管理员统一部署（企业功能）

### Q: 评估结果在不同模型上会不同吗？

A: 会。建议在目标模型上运行评估。Skill Creator 支持跨模型比较。

### Q: 技能更新后如何处理现有用户？

A: 版本化发布。用户可以选择升级时机。评估结果与版本绑定，便于比较。
